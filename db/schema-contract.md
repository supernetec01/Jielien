# Database contract — PostgreSQL phase 1

This contract describes **implemented schema**, not AVAKids' private database. Migrations: `db/migrations/001_core.sql` and `002_bank_transfers.sql`; runner: `migrate(pool)` from `db/migrate.mjs`.

There are **35 domain tables**, plus `schema_migrations` (36 total). Only the role/permission/primary-warehouse defaults are inserted by SQL. Catalog and legacy-order import belong to the store/import code.

## Shared conventions

- Entity IDs: `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`. IDs are positive, explicit legacy IDs are allowed. After importing explicit IDs, advance the corresponding identity sequence before normal inserts.
- Storefront product ID remains **`product_variants.id`**, preserving previous cart/wishlist IDs and variant detail URLs. `products.id` identifies the parent product; do not reinterpret old variant IDs as a parent lookup.
- External order ID remains **`orders.order_number`** (`JL...`); relational joins use the new internal **`orders.id`**.
- Prices/totals are integer VND in `BIGINT`, with safe-integer bounds where values are supplied by the storefront. Convert pg's bigint strings deliberately; do not introduce floating-point currency calculations.
- Timestamps: `TIMESTAMPTZ`, defaults `CURRENT_TIMESTAMP`. `updated_at` is changed explicitly by the application; there is no hidden trigger.
- Selling entities are deactivated, not deleted. Foreign keys use `RESTRICT`; only mapping/join tables use `CASCADE`.
- Parameterized queries are required. The runner operates in the pool connection's current `search_path`; no `public` schema is hardcoded.
- `schema_migrations(version TEXT PK, checksum TEXT, applied_at TIMESTAMPTZ)` records immutable SHA-256 migration checksums. A missing or modified applied migration is an error. The runner uses a transaction and advisory lock to serialize migration attempts.

Default roles: `customer`, `admin`. Default permission codes: `catalog.manage`, `orders.manage`, `inventory.manage`, `users.manage`, `audit.read`. Admin receives all five; customer receives no management permission. There is **no default administrator account or password** in the migration.

Profile changes accept only full name/email; changing or removing email requires the current password. Password changes hash the new password, revoke all sessions and record a nonsecret audit event in the same transaction. The owner can edit/delete addresses; deleting the default promotes the most recently created remaining address. Orders retain their own address snapshots.

## Cart and orders

| Table | Columns and relationships |
| --- | --- |
| `carts` | `id` PK; `user_id` nullable FK; `session_id` nullable; at least one owner field required; `status` active/converted/abandoned; `created_at`, `updated_at`. Unique active cart per nonnull user or guest session. |
| `cart_items` | `id` PK; `cart_id` FK; `variant_id` FK; `quantity` 1–99; UNIQUE (`cart_id`, `variant_id`) |
| `orders` | `id` internal PK; `order_number` UNIQUE external code; `user_id` nullable FK; `status`; `recipient_name`, `recipient_phone`, `recipient_email` nullable; `address_detail`, `province`, `district`; `subtotal`, `discount_total`, `shipping_fee`, `grand_total`; `coupon_code` default empty; `payment_method` cod/bank_transfer; `note`; `access_token`; `idempotency_key` UNIQUE; `fingerprint`; `created_at`, `updated_at` |
| `order_items` | `id` PK; `order_id` FK orders.id; `variant_id` FK; `sku_snapshot`, `name_snapshot`, `image_snapshot`; `quantity`; `unit_price`, `line_total` |
| `order_status_history` | `id` PK; `order_id` FK; `old_status` nullable for initial creation; `new_status`; `changed_by` nullable FK users; `note`; `created_at` |

Order statuses: **pending, confirmed, processing, shipped, delivered, cancelled**. Schema constrains valid values; the service enforces allowed transitions.

Order amounts satisfy `grand_total = subtotal - discount_total + shipping_fee`, `0 <= discount_total <= subtotal`, all amounts nonnegative. Item amounts satisfy `line_total = unit_price * quantity`, with positive quantities.

`access_token` preserves the old random order-view token so existing session confirmation links can still work; it is not an authentication session token. New `user_sessions` instead stores token hashes. Neither token is shown in admin list/audit metadata.

Legacy import must preserve order number, phone normalization, access token, idempotency key/fingerprint and snapshots. It must not regenerate old line prices from today's catalog. Old JSON is not the authoritative storage after import: the application reconstructs its API response from orders/items.

## Payments, warehouse and shipping

| Table | Columns and relationships |
| --- | --- |
| `payments` | `id` PK; `order_id` FK; `provider` default manual; `method` cod/bank_transfer; `amount`; `status` pending/paid/failed/cancelled/refunded; `paid_at` nullable; `created_at`. Multiple payment attempts per order are allowed. |
| `bank_transfer_details` | `payment_id` PK/FK payments.id (one snapshot per payment); `bank_bin` 6 digits; `bank_name` 2–100 chars; `account_number` 6–30 digits; `account_name` 2–100 chars; `reference` UNIQUE, 1–25 alphanumeric/space/hyphen chars starting alphanumeric; `amount` positive safe-integer VND; `qr_payload`; `created_at`. No bank login credentials. |
| `payment_events` | `id` PK; `payment_id` FK; `provider_event_id` UNIQUE; `event_type`; `received_at`; `payload` JSONB. Stores accounting events, not payment-card data. |
| `warehouses` | `id` PK; `name`; `type` normal/damaged; `status` active/inactive. Seeded warehouse ID 1: Kho chính, normal/active. |
| `inventory_balances` | composite PK (`warehouse_id`, `variant_id`), both FK; `on_hand`, `reserved`; `updated_at`. Checks `0 <= reserved <= on_hand`. |
| `inventory_movements` | `id` PK; `warehouse_id`, `variant_id` FKs; `quantity_change`; `reserved_change` default 0; `movement_type`; `reference_type`, `reference_id` nullable; `actor_id` nullable FK users; `reason`; `created_at`. At least one of physical/reserved quantity changes must be nonzero. |
| `inventory_reservations` | `id` PK; `order_id`, `variant_id`, `warehouse_id` FKs; `quantity` positive; `status` active/consumed/released; `created_at`, `updated_at`; UNIQUE (`order_id`, `variant_id`, `warehouse_id`) |
| `shipments` | `id` PK; `order_id` FK; `carrier`, `tracking_number` nullable; `status` pending/ready/processing/shipped/delivered/cancelled; `created_at`, `updated_at`. Multiple shipments per order are representable. |
| `audit_logs` | `id` PK; `actor_id` nullable FK; `action`, `entity_type`; `entity_id` nullable text; `metadata` JSONB; `created_at`. Metadata must not contain passwords, raw session tokens or entire customer payloads. |

Bank transfers are enabled only with valid server-side `BANK_BIN`, `BANK_NAME`, `BANK_ACCOUNT_NUMBER` and `BANK_ACCOUNT_NAME`. The service snapshots receiving details, server-calculated amount, unique order reference and locally generated NAPAS/EMVCo payload at checkout. Snapshots survive later configuration changes. No QR or banking API request is required.

Payment starts pending. Only staff with `orders.manage` may confirm receipt after checking their bank; there is no provider webhook, automatic reconciliation or buyer “mark paid” action. Confirmation locks the order/payment and creates an idempotent `bank_transfer.confirmed` event plus audit. Unpaid transfers cannot be shipped/delivered; paid transfers cannot use ordinary cancellation because refunds are not yet implemented. QR instructions are hidden after payment or cancellation, while snapshots are retained.

Movement types: **opening, reserve, release, sale, adjustment, transfer, return, legacy_import, receipt**.

Available inventory is `on_hand - reserved` in active **normal** warehouses. Damaged warehouses never contribute sellable stock. Creating a pending order reserves inventory; cancellation releases reservation; shipping decreases physical and reserved quantities together. Both balance and ledger/reservation/order updates occur in a transaction with locked balance rows. Repeating an order request must not reserve twice.

Legacy SQLite stock is already decremented at order creation. Import must not subtract it again; either retain legacy deductions with consumed reservations or reconstruct on-hand/reserved consistently so available stock after import exactly equals legacy stock. Record the chosen interpretation in the import summary.

## Promotions and import journal

| Table | Columns and relationships |
| --- | --- |
| `promotions` | `id` PK; `name`; `discount_type` fixed/percentage/shipping; `discount_value`; `minimum_order`; `maximum_discount` nullable; `start_at`, `end_at` nullable; `status` active/inactive; `priority`; `stackable` false by default |
| `coupons` | `id` PK; uppercase `code` UNIQUE; `promotion_id` FK; `usage_limit` nullable positive; `used_count` nonnegative; `expires_at` nullable; `status` active/inactive; usage count cannot exceed a nonnull limit |
| `coupon_redemptions` | `id` PK; `coupon_id` FK; `user_id` nullable FK; `order_id` FK UNIQUE; `used_at` |
| `legacy_imports` | `source_key` TEXT PK; `imported_at`; `summary` JSONB containing import metadata/counts, not customer records |

Only one coupon is used per order in phase 1. `order_id` UNIQUE in redemptions prevents accidental stacking. Check dates, conditions and the coupon usage limit inside the same transaction as order creation. An idempotent retry reuses the existing redemption.

## Not implemented by this migration

Phase 2/3 remain explicit backlog: OTP delivery, online payment gateways/refunds/invoices, batch/expiry stock, cross-warehouse transfer workflow, carriers/webhooks, full return workflow, member points, customer reviews, flash-sale quotas, dynamic bundles, CMS/media/livestream, multi-channel orders and translation API/cache. Their absence is preferable to claiming that unused placeholder tables implement those services.

Backups and migration validation remain required before switching the live app: consistent SQLite backup including WAL, a single import transaction, comparison of all legacy IDs/totals/stock, FK and integrity checks, repeat-import verification and regression tests. The original SQLite file is not deleted by schema creation.
